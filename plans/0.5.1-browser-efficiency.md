# Browser efficiency plan for 0.5.1

Second source review dated **2026-10-17**, against clean fork HEAD
`d6d021ed68af250f8b1679c12c4fa69ba449c6ac`. The strongest current-game opportunity
is application label visibility/work reduction, followed by a measured decision
on preserving order while reducing camera flushes. Library 0.5.1 should stay
bounded to draw-capacity correctness and owned browser input termination.
Atlas growth copying becomes conditional work, separate from eager startup cost.
Stream-buffer/framebuffer changes remain experiments without browser GPU evidence.

This changes the first plan's priorities: bitmap labels are exercised every game
frame, whereas the game has no mouse/touch or custom mesh usage and browser
loading/gameplay does not call TTF drawing. Real generic library bugs still
warrant fixes, but they are not established game bottlenecks. No optimization,
version bump, upstream patch adoption or game change is included in this review.
Open work continues to belong in the ignored `PUNCHLIST.md`; this document
supplies design and acceptance criteria, not a second status tracker. Repository
source paths and shell commands below are relative to the repository root.

### Retained first-pass generated-scene diagnostic

The existing generated fixture draws 1,200 tiles, 64 ships, 512 projectiles,
32 eight-glyph labels and a HUD (rectangle plus 16 glyphs). Both variants issue
these in the same visible order with the same source sheets and geometry.
The `camera` variant changes cameras around each label; `screen` groups the
screen-space labels. This tests an application arrangement, not an engine patch.
Unlike the game,
all fixture ships/projectiles precede a contiguous label phase; fixture labels
have no separate shadow draw, and ships/projectiles share one sprite sheet.
Its 37→6 draws therefore cannot predict the unchanged game's draw count.

The first pass added `--submissions` instrumentation that wraps WebGL methods
**only after each timing trial**, during the existing verification frame, and
restores them at the next
RAF callback. It includes end-frame submission and commit; no counter wrappers
run during the measured CPU/RAF trials. It observes the paired runtime's
`drawElementsInstanced` path (including WebGL1's ANGLE adapter), plain draw paths,
upload byte lengths, framebuffer/texture binds, buffer allocations and texture
mutations. Native receiver, returned value, exceptions and original method
properties are preserved. Node tests cover these contracts; Python negatives
reject missing work/calls, reordered observations and warm-frame resource churn.
Default browser commands do not enable the instrumentation.

All four cells passed: Chrome **155.0.8059.79**, ChromeDriver **155.0.8059.79**,
Firefox **158.0**, GeckoDriver **0.37.1**, release WASM, Rust **1.98.1**,

### Application follow-up acceptance and stop conditions

**First: skip invisible work.** Compute screen label bounds including text
width, scale, shadow offset, energy/name placement and attached-child offsets;
a ship center outside the viewport can still have visible text or a large LVZ
sprite. Cull each presentation extent conservatively before glyph enqueueing,
and before formatting where cached/bounded metadata makes that possible.
Preserve order for every surviving draw. Cache immutable bitmap sheet columns
separately; this avoids repeated app lookups, not driver queries. High confidence
in the path, unknown population/CPU benefit. Start with offscreen names, not a
blanket entity-center cull or simulation pruning.

**Then: decide whether camera work merits change.** An in-order world-camera
label helper must transform all glyph corners from screen to world coordinates,
including the one-pixel shadow and text scale; it cannot just change the label
anchor. Preserve exact ship→shadow string→foreground string→next-ship order.
Alternating ship/font textures still split draws. Worse, eliminating flushes can
retain more simultaneous draw slots: each default slot requests
10,000×40 + 5,000×2 = **410,000 payload bytes** of GPU buffers, reused across
flushes but retained at high water. Twenty additional slots request 8,200,000
bytes, excluding driver overhead. Fewer setters is not sufficient acceptance.
Grouping all labels after ships is a visual policy change; require an explicit
app decision before using that design. Do not alter global camera semantics to
make an app rearrangement appear free.

In the separately authorized app task, start with a CPU/submission baseline at
a fixed entity/visibility history and ordinary versus debug modes. Require exact
old/new visible pixels in overlapping ships, shadows, labels, flags/turrets,
LVZ/HUD and edge/camera/spectator cases; verify offscreen skips leave simulation,
authority and presentation traces consistent. Count labels/glyphs culled, camera
flushes, total draws/bytes, GPU buffer slot high water/requested bytes and app
allocations. Measure whole-frame CPU including end-frame submission and retained
memory alongside cadence. Stop or revise if only setters fall while memory,
frame CPU or pixels regress. Existing synthetic counts establish feasibility,
not a game acceptance target. App fixtures/assets/tests remain in the game repo;
no app work or acceptance was executed in this review.

## Recommended bounded 0.5.1 scope

Capacity and input below are the two proposed release batches. Their ordering is
library correctness priority, separate from the higher likely app efficiency
return above. Neither depends on the app follow-up, a new buffer strategy, or
TTF growth work. Each begins with a failing focused regression before a fix.

### Capacity batch: correct boundaries before tuning buffer sizes

**Evidence/priority:** shared Macroquad correctness, with no custom mesh or
capacity override in the current game. `>= max - incoming` unnecessarily splits
exact-fit batches;
independent clipping of vertices/indices can leave indices outside retained
vertices; configurable capacities can exceed the u16 rebase domain. Concrete
source-level examples (not newly executed engine regressions): with
`max_vertices=8,max_indices=12`, two four-vertex/six-index quads split because
`4 >= 8-4` and `6 >= 12-6`, although both fit. With a five-vertex mesh and
`max_vertices=4`, an index of 4 survives index-slice clipping while its vertex
is removed. With capacities above 65,536, accumulating valid small meshes can
make the u16 offset cast/add wrap (or panic in debug). These are
source-derived failure conditions, not failures reproduced by the fixed scene.
The default 5,000-index limit fits 833 quads (4,998 indices) under either `>=`
or `>`; the next quad reaches 5,004. Therefore exact-fit correction alone cannot
reduce default quad batches in the game or retained scene. Its value is fixing
exact boundaries/custom meshes, not tuning ordinary sprites. The scene supplies
matched-work/pixel oracles but does not reproduce these failures. Changing a
large capacity by intuition could increase
retained GPU memory per draw slot without reducing camera fragmentation.

**Approach:** first create focused boundary cases for exact fit, one over, invalid
indices, capacities zero/small/above the u16 domain and capacity change while
geometry is queued. Validate capacities/indices before allocation or upload.
Never retain an index
outside its vertex slice or partially clip topology. For oversized single meshes,
first document the supported contract and compatibility decision; fail-fast is a
proposal, not permission to reject every formerly accepted configuration. Then
permit exact fits when
validated index rebasing remains representable. Preserve triangle/line topology,
custom-material uniforms, texture order and capture state. Keep default limits
and per-draw buffers initially; automatic arbitrary-mesh splitting or a new mesh
API is outside this batch. Existing hidden `gl_set_drawcall_buffer_capacity`
resets queued draw count; decide flush-versus-reject explicitly rather than
silently losing pending work during the fix.

**Compatibility/risk:** valid rendering order and public signatures remain;
invalid/previously truncated geometry may now fail early, but unchanged signatures
alone do not prove patch compatibility. Public `Conf` capacities and the hidden
but public capacity setter can be used by consumers. A configured vertex capacity
above 65,536 can still support valid small batches; prefer a safe effective batch
limit/split over blanket rejection unless separately justified. Index *count*
can exceed 65,536 while all u16 index *values* remain valid; do not cap the former
at the latter. The u16 storage domain contains 65,536 vertices / maximum value 65,535,
but the actual renderer can reserve that final value; see the implementation
contract below. Specify supported inputs, queued-capacity
changes and panic/flush behavior before declaring 0.5.1 compatibility; test
arithmetic and avoid unchecked casts or release-only wrap behavior.

**Implementation contract and WebGL2 correction:** indexed geometry is accepted
whole or rejected before enqueue; single meshes above either effective capacity
and local indices outside their vertex slice panic. Empty index slices submit
nothing; zero and tiny capacities remain valid configurations when submitted
geometry fits. Configurations above the vertex domain remain accepted and use a
safe effective limit. Index count is independent and must fit signed draw-count
and buffer-byte limits. The hidden public capacity setter rejects queued geometry
before changing buffers; callers can flush using `set_default_camera()` or change
capacity before drawing at the start of a frame.

A complete-pixel boundary regression established a constraint missing from the
original plan: [WebGL2 fixed primitive restart](https://registry.khronos.org/webgl/specs/latest/2.0/#NO_PRIMITIVE_RESTART_FIXED_INDEX)
is always enabled, and index 65,535 in an unsigned-short draw ends a primitive
instead of addressing a vertex. The effective ceiling is therefore **65,535
vertices / maximum emitted index 65,534 on actual WebGL2**, and **65,536 /
65,535 on WebGL1 and the supported native path**. Derive this from the actual
context, including Auto/fallback, and retain it when changing capacities. On
WebGL2 an indexed mesh with 65,536 vertices is oversized and rejected before
queueing; supporting it would require another index representation and is outside
this batch. Preserve independent index counts above 65,536. The regression
requires complete triangles on both sides of that backend-specific split;
checking index storage bounds or GL errors alone misses the lost triangle.

**Acceptance:** exact upload/index bounds verified at the actual backend,
complete triangle/line pixels around capacity boundaries, and no dropped or
reordered sprites. For the unchanged generated scene, retain 2,049 quads,
327,840/24,588 upload bytes and exact pixels in all four browser/GL cells;
record any draw-count change with an explained boundary case. Reject invalid
cases before GL and preserve all existing valid mesh/material/resource tests.
Measure requested GPU allocation/high-water slots if later capacity tuning is
proposed; no buffer-memory improvement claim comes from this plan.

### Input batch: complete owned browser input termination

**Evidence/priority:** generic browser correctness, not current keyboard-only
game performance. Canvas-only release and the Cancelled→mouse-up omission
above are source-confirmed correctness gaps. Touch cancellation removes contacts,
per [W3C Touch Events §5.8](https://www.w3.org/TR/touch-events/#the-touchcancel-event).
No real-browser regression reproducing these gaps was added in this planning
batch; obtain one before implementation. Capable desktop touch devices are
relevant, but this does not imply mobile platform qualification.

**Approach:** track buttons whose press began on the canvas and deliver one
release when their mouseup reaches the owning window; preserve relative and
pointer-lock coordinates. Ignore releases for unrelated DOM controls. Decide
and document release ordering across blur, canvas exit and duplicate mouseup.
Treat Cancelled as a terminal event for the simulated mouse owner; account for
multiple touches so cancelling an unrelated finger cannot release a surviving
primary contact. The current implementation maps *every* touch start/end to the
left button; it has no primary-contact policy. Defining one changes observable
multitouch behavior. Do not silently bundle that redesign into a patch: first
specify the compatible termination rule and regression, or isolate/defer the
policy change while fixing the established single-touch Cancelled gap. Preserve
opt-out touch simulation and event-loop wake behavior.
Adapt #602's small listener change; do not copy its unconditional global release.

**Compatibility/risk:** no public signature change or autoplay workaround.
Applications may observe the previously missing release; duplicate releases and
changed focus/mouse ordering are the main hazards. Avoid replacing all browser
input with Pointer Events in this release. Maintain runtime input/output pairing.

**Acceptance:** deterministic press→outside release, press→cancel, duplicate
release, unrelated document mouseup, pointer-lock and blur/return sequences;
exactly one owned release and no stuck held state. Real WebDriver mouse action
outside canvas in all four Chrome/Firefox WebGL1/2 fixture cells, plus synthetic
cancel dispatch into the real WASM handler (label it synthetic, not physical
hardware acceptance). Check multi-touch bookkeeping, touch-simulation disabled,
blocking-loop wake and unchanged key/focus behavior with focused tests. Keep
existing actual audio-resume/cancellation assertions when running full acceptance.

## Conditional atlas and startup work

This is removed from the mandatory third 0.5.1 batch. No current browser game
TTF growth path was found, and [upstream-issues.md](../docs/upstream-issues.md)
already explains that deferral. First measure generated bitmap-only cold init
versus first TTF/UI use: three eager atlas allocations, font parsing, UI ASCII
rasterization and empty-UI frame work are separate from growth. Compare a narrow
checked zero-fill/row-copy improvement with laziness only after attribution;
laziness adds first-use and input/shutdown ownership risk. Keep the font parser
maintenance decision separate; neither row copies nor laziness clears an advisory.
No startup measurement or resource-removal claim is added here.

If an exercised cost justifies the work, use the following bounded design.

**Evidence/priority:** #1076 removes explicit full-image clone and per-pixel
copies in code currently present. This is a bounded CPU/allocation reduction
candidate; the fixed bitmap scene does not exercise TTF atlas growth, so it
cannot establish a measured benefit for this change or Zubspace's bitmap font.

**Approach:** adapt move-out/zeroed-image/row-copy helpers while preserving
checked sizes, deterministic height/width/position repacking, gaps, SpriteKey
identity and deferred graphics ownership. Use source image plus rect to avoid
per-glyph temporary Images. Keep `Image::sub_image` behavior (including bounds,
zero-size and validation) explicit; do not adopt a broader public image API
change incidentally. Separately inspect the duplicate upload after atlas texture
replacement; eliminate it only with a regression proving new pixels were already
uploaded, filtering retained and deferred deletion remains correct. Otherwise
leave that micro-change for follow-up.

**Compatibility/risk:** no public signature change, packing/UV/pixels must remain
identical. Preserve RGBA bytes, zeroed padding, atlas growth limits and panic
behavior; preserve checked Image construction and validated rectangle behavior.
No texture lifetime/thread-safety rollback from 0.5.0 is acceptable.

**Acceptance:** patterned multi-row sprites with nonzero source offsets and
mixed heights, several growth steps, deterministic packing, zero-size/boundary
rectangles, exact whole-image comparison and allocation counts. A generated
TTF/text fixture must force actual growth in Chrome/Firefox WebGL1/2, verify
independent glyph/background/overlap pixels, old/new texture deletion and GL
errors. Collect repeated cold/growth CPU and allocated/copied byte diagnostics
separately from warmed steady draw trials. Require removal of the identified
clone/temp-image path and pixel equivalence; no hardware-independent millisecond
threshold or promised FPS gain. Default scene and ownership/UI gates still pass.
